# 전 카드사 통합 DB 구축·유지 작업

사용자는 전체 카드의 상품설명서를 대조해 정교한 공통 DB를 완성하고, 사용 한도 때문에 중단되면 다음 실행에서 이어서 완료하도록 승인했다. 기존 사이트 접근 권한과 수동 편집은 보존한다. 승인이나 착수 여부를 다시 묻지 않는다.

## 현재 단일 기준

- 상품키는 발급사와 공식 상품코드다. 신용/체크, 발급은행, 디자인/브랜드·대상 변형을 임의 합치지 않는다. 22개 발급기관, 초기 1,536개 기록을 모두 보존한다. 신상품은 신규 공식 상품코드로 추가한다.
- `card_normalized_rows`는 상품, 혜택, 실적구간, 한도/제외조건, 적립모델, 결제판정, 문서, 원문표를 상품·혜택키로 연결한다. `card_review_queue`가 누락사유, 단계, 시도수, 다음재시도를 보존한다.
- 무실적 0, 확인된 무제한, 미확인을 구분한다. 카드사 기본값으로 채우지 않는다. 자동 추출 후보를 확인값으로 승격하려면 해당 상품·혜택 범위의 공식 근거가 필요하다.
- 카드사마다 다른 제외 문구는 상품권·선불카드 충전, 아파트 관리비, 국세, 지방세, 공과금, 4대보험, 등록금, 무이자할부, 연회비·수수료, 할인받은 이용금액의 공통 항목으로 정규화한다. 전월실적 인정과 혜택 제공을 각각 가능·불가·미확인으로 저장하며, 원문에 없다는 이유만으로 가능 처리하지 않는다. 하나의 대표 판정을 연간실적·기본/특별 적립·라운지·발레·멤버십 등급·연간보너스에 일괄 적용하지 않는다. 각 부가혜택의 실적 산정 범위와 제외 목록을 `eligibilityRules.scope`로 분리하고, 공식 문구가 전월실적만 제외한다고 명시하면 연간실적 판정을 별도 확인한다.
- 전월실적은 혜택별로 기록한다. 이상/초과, 국내 한정, 본인·가족 합산, 승인/매입일, 신규유예, 할인받은 거래의 실적 제외를 포함한다.
- 영역/통합/공유/건당/일월연 횟수, 기본+추가 중복, 초과 후 기본률, 선택형, 결제채널, 대상 가맹점과 제외를 모두 확인한다. 후보 실적표는 해당 혜택의 적용범위가 확인되기 전 계산에 사용하지 않는다.
- 피킹률은 연회비·바우처·연간 보너스를 제외한다. 마일/포인트는 명시된 평가 가정(현재 대한항공 20원, ALL 30원)을 사용하며 환산값임을 표시한다. 동일 결제의 확인된 해외수수료 면제는 합산한다. 부과 수수료·ATM·환전 우대는 합산하지 않는다. 최소 실적 충족 뒤 당월 동일 예산에서 가능한 소비배분을 계산하되, 실적 제외 소비로 인한 추가 소비와 지속 사용 조건은 별도 설명한다.
- 한 거래를 여러 업종에 중복 배분하지 않는다. `spendingPlans`는 확인된 독립 소비영역과 중첩형 공유한도만 지원한다. 교차형 한도, 미확인 건당/횟수·최소 결제 조건, 월정액 조건은 별도 모델·검증이 필요하다.
- 완료는 모든 누락조건 해소와 계산 검증까지 통과한 상태다. 원문 확보/정규화 저장만으로 완료로 표시하지 않는다. 보조금·무이자·무료 서비스 등 비금전 혜택의 금전환산을 임의 생성하지 않는다.

## 매 실행의 순서

1. 연결된 Sites `get_site`로 현재 사이트와 기존 자동화를 읽는다. 제공되는 `siwc_bypass_bearer_token`은 이 사이트의 `OAI-Sites-Authorization: Bearer ...` 헤더로만 사용하며 출력·저장하지 않는다. 이 접근은 로그인 사용자를 만들지 않는다. 사이트의 소유자 전용 접근경계를 유지한다.
2. `GET /api/sync/cards`로 초기 정규화 커서와 작업목록을 읽는다. `seed.done=false`이면 `POST /api/sync/cards`에 `{"action":"initialize","limit":20}`를 커서 완료까지 순서대로 호출한다. 커서는 성공한 묶음 뒤에 저장된다. 202는 진행 중이므로 중복 실행하지 않는다.
3. 하루 처리 목표는 검증·저장 성공 50건이다. `GET /api/sync/cards?limit=50`의 `dailyTarget`과 다음 상품을 읽고, 같은 카드사를 10건 안팎으로 묶어 공식 문서 형식과 공통 조건을 재사용하되 근거는 상품코드별로 분리한다. 완료에 가까운 상품을 우선하되 카드사를 순환하고 실패한 같은 상품만 반복하지 않는다. 상품별 `GET /api/sync/cards?card=<ID>`의 card, contentHash, normalized, sourceChange를 보존한다.
4. 공식 원문을 묶음 확인한다. `POST /api/sync/cards`의 `action=batch_source,items=[{cardId,url}]`은 최대 10건씩 병렬 수집하며 하루 3~5묶음을 처리한다. 단건 `action=source`도 유지한다. HTML 본문·표는 후보로 확보하고 PDF는 해시·URL만 보존한다. PDF는 지원되는 웹/PDF 도구로 본문·페이지를 읽는다. 읽기 실패·동적 로그인은 지원되는 검색으로 공식 상세나 실제 상품설명서를 확보하고, 불가능하면 실패를 기록한다. 설명서 링크가 있다는 사실을 본문 확인으로 대체하지 않는다.
5. 카드의 혜택·실적·한도·제외·요율·판정을 공통 규격으로 채운다. 숫자로 계산 가능한 `rewardRates`, 복수 영역을 배분하는 `spendingPlans`, 상품별 근거 `documents`, `eligibilityRules`를 저장한다. 연간 회원등급·연간 보너스·공항 라운지·공항/호텔 발레·리무진·골프·보험 등 카드별 부가혜택도 각각 scope를 만들고, 결제 항목별 실적 인정 여부와 본인/가족 합산·회원 자격·승인/매입 기준을 확인한다. 완성하지 못한 금전 혜택이 남으면 `rewardCoveragePending=true`, `rewardModelComplete=false`다. 브랜드 안내만으로 카드 전체 약관을 대체하지 않는다.
6. 경계값(구간 직전/정확히/직후), 기본+추가와 초과 후 기본률, 공유한도, 건당/횟수, 중복배제, 실적제외, 환산가치 변경, 요약/상세 일치를 계산·검증한다. 통과한 실제 근거를 `calculationValidation`에 기록한다. 예외(`no_spend_requirement` 등)는 원문에서 확인한 경우만 쓴다.
7. 검증된 항목은 `POST /api/sync/cards`의 `action=batch_import,items=[...]`로 최대 50건을 한 번에 저장한다. 각 items 원소는 기존 단건과 동일하게 card, expectedHash, evidence, reviewedSourceHash를 가진다. 각 상품은 독립 판정되어 일부 충돌·실패가 있어도 나머지는 저장된다. 검증 모델 변경에는 실제 공식 발췌가 필수다. 409 충돌은 다시 읽고 합치며 수동편집은 덮어쓰지 않고 보류한다. 단건 `action=import`도 예외 재처리에 유지한다.
8. 저장 직후 성공·보류 건수를 읽고, 성공 상품은 표본이 아니라 전부 `GET /api/sync/cards?card=<ID>` 또는 묶음의 contentHash와 `/api/catalog`로 연결·피킹률·종료 상태를 검증한다. 하루 50건 미만이면 남은 큐를 다음 카드사 묶음으로 계속 처리한다. 실패/한도/시간 종료 때 `action=checkpoint,cardId,note,retryHours=24`로 다음 실행의 재개사유를 남긴다. 이미 성공한 상품은 다시 작업하지 않는다.

## 신상품·공시·이벤트·캐시백

- `data/card-source-registry.json`의 43개 공식 목록/공시 링크와 `data/coverage.json`의 발급기관 범위를 사용한다. `action=watch,limit=3`을 가장 오래 미확인된 출처부터 호출해 전 출처를 순회한다. 결과의 관측 링크를 공식 목록/공시에서 확인한다. 일부 페이지·동적 응답이나 product_sample을 전수 신규상품 확인으로 표현하지 않는다. 페이지 끝까지 확인하고 신상품, 발급중단, 약관변경을 상품코드로 구분한다.
- 변경감지는 검토 후보다. 실제 신상품/조건변경은 상세·설명서 확인 후 import한다. 읽기 실패를 변경없음으로 기록하지 않는다. 공식 원문 변경이 감지된 기존 카드의 최고피킹률은 재대조 전 보류된다.
- 카드사 이벤트·발급 캐시백은 기존 이벤트 갱신 작업이 `SCHEDULED-UPDATES.md`의 수집/import 절차를 수행한다. 카드 검토 작업에서 발견한 관련 이벤트는 원문과 검토 후보를 남긴다. 공식 상세의 기간, 대상, 응모, 실적, 지급, 제외·중복·환수 조건을 확인한다. 최대광고금액과 확정액, 선택형 혜택을 구분한다. 공시만 있는 조건 미확정 이벤트를 확정캐시백으로 넣지 않는다.
- 새 자동화를 추가하지 않는다. 기존 카드 검토 작업(매일 오전 6시 Asia/Seoul)은 DB 완성과 신상품·공시 대조를 맡고, 기존 이벤트 작업(매일 오전 6시 Asia/Seoul)은 이벤트·발급 캐시백을 맡는다. 두 작업의 상품 갱신 충돌은 최신 해시와 잠금으로 막는다. 완성 후에는 카드 작업을 신상품·조건 변경 유지에 사용한다. 종료/권한/실패/중요 진행 변화는 알리고, 같은 상태의 무변화 알림은 생략한다.

## 코드 또는 배포 스냅샷을 고칠 때

Sites 스킬로 해당 프로젝트 소스를 열고 기존 ID·권한을 보존한다. `node --import ./scripts/register-typescript.mjs scripts/build-normalized-catalog.mjs`, `node --import ./scripts/register-typescript.mjs scripts/refresh-presentation-data.mjs`, `node scripts/sync-source-data.mjs build`로 스냅샷을 일관되게 만든다. `check-normalized-catalog.mjs`, `check-reward-policies.mjs`, `check-foundation-database.mjs`, TypeScript, 빌드 후 `check-normalization-writer.mjs`를 해당 변경에 맞게 검증한다. 일상 조건 갱신은 위 저장 API를 사용해 재배포 없이 처리한다. 다운로드 JSON/엑셀은 배포 스냅샷 날짜를 표시하며 현재 DB와 구분한다.

## 사용자 보고·피킹률 표

사용자는 2026-10-10부터 설명과 작업보고를 간결한 표로 표시하도록 요청했다. 혜택별 적립·할인 / 동일 결제 수수료 면제 / 합산 피킹률 / 전월실적 / 한도 / 검토 상태를 구분한다. 클래시 트래블은 해외 적립 4% + 수수료 면제 1.25% = 5.25%이며 국내 전월실적 100만원 초과, 국내·해외 적립 통합 월 10만점 조건을 표시한다. 이하/이상/초과, 국내 한정, 하나로가족고객 등 자격 조건을 요율 옆에서 확인할 수 있게 기록한다.
